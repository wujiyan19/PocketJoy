# 鸿蒙应用默认开发

将玩趣盒的原生体验与工程约定用于新的鸿蒙应用及现有应用扩展：清楚的内容层级、轻量实体卡片、系统语义色、自然的交互反馈，以及可验证的数据和业务逻辑。

这些是用户的默认偏好，适用于鸿蒙应用开发，不要求显式输入技能名。用户本次要求与目标项目的 `AGENTS.md` 优先；已有设计系统、SDK、服务端技术栈和数据契约应沿用。玩趣盒的品牌、游戏目录、页签名称和历史网络协议属于项目实例。

已有应用的局部修改仅落实本次相关约定，主题设置、状态页和新基础设施按任务范围建设。

## 实现原则

- **从零开发先查 GitHub。** 先找成熟项目，核对维护情况、许可证、鸿蒙适配与需求匹配；有合适项目时优先复用或基于它改造，没有合适项目再自行实现，并简述检索结论。已有项目的小改动直接复用现场代码。
- **防过度防御。** 针对真实输入、可达失败和已确认问题实现处理。几乎不会发生的边界或并发情形，先说明发生条件、概率依据或不确定性、代价，经用户确认后再加；不为“理论上更稳”扩张代码。
- **入口单次校验。** 外部 JSON、持久化、Want 和网络消息在各自信任边界完成一次解析和校验，内部以明确类型流转；不在页面、ViewModel、Model 重复检查同一组字段。领域规则在执行业务操作处判断，服务端仍须独立验证客户端输入。
- **拒绝提前抽象。** 单次使用逻辑就近内联，单函数能清楚表达就不拆无意义 helper；只有实际复用或明确职责需要时才加组件、ViewModel、Repository 或兼容层。
- **控制异常处理。** 仅在需要处理 API/解析/I/O 失败的边界使用 `try/catch`，说明恢复或失败语义；不逐层捕获、不空 catch，不以默认值伪装读写成功。

## 开始开发

先确认目标工程、已有未提交改动、模块与资源结构、SDK/API Level、状态管理版本、导航方式、数据存储和实际后端。需要新增依赖、权限或接口时先查现有实现与官方定义；不确定的 HarmonyOS API/语法应搜索华为官方文档，并核对目标 SDK 声明、导入、设备支持与权限。

读与本次工作相关的参考资料：

- 写 `.ets` 或 ArkTS 共享代码前，读 [ArkTS 与 API 约束](references/arkts-and-api.md)。
- 做页面、组件、素材或动效时，读 [界面与交互](references/ui-and-interaction.md)。
- 做状态、业务、本地存储、接续、联网或配套服务端时，读 [架构、数据与后端](references/architecture-and-backend.md)。
- 构建、测试和交付时，读 [构建验收与来源](references/validation-and-sources.md) 的相关部分。

对于 LittleGames，直接复用 `DesignTokens`、`HarmonyMotion`、现有公共组件、路由注册及数据服务。对于新工程，按功能需要建立最小实现，不复制整套目录或把 LittleGames 当作运行依赖。编译 SDK、target SDK、最低兼容版本分别核对；新 API 的使用不能靠擅自提高最低版本解决。

## 默认前端

- 采用 HarmonyOS 原生组件与 Navigation；新工程在目标 SDK 支持时优先 ArkUI V2，已有工程沿用其状态管理版本。组件负责展示和事件，复杂业务按需交给 ViewModel/Model，不为简单页面强制创建全套分层。
- 应用外壳使用系统背景、文字色与强调色；主卡浅色白、深色中性灰。业务插画和棋盘拥有独立双主题资源。主内容与控件分层，只有浮层使用轻投影和按需材质。
- 共享页头、卡片、分组、设置行和确认弹层。沿用统一圆角、间距、字体、触区和主次按钮关系，避免每页自建一套样式。
- 文案、颜色、新增尺寸与动效参数资源化；同时维护目标工程所有语言目录。新应用默认支持跟随系统、浅色、深色，并保存用户选择；已有应用沿用其主题入口。
- 从当前内容区域的可用宽高计算布局；按产品支持范围覆盖小窗、分屏、横屏、平板、长文本和放大字号。安全区等动态值需能驱动视图刷新，不能仅在启动时取数字快照。
- 原生按压、物理弹簧选中、独立遮罩淡入和快速退场构成默认反馈。仅动画变换与透明度等合适的非布局属性；复杂动画子树使用 `renderGroup(true)`。
- 按真实业务路径表达内容、加载、空态或失败，存在可重试操作时提供对应重试。保留筛选、返回和滚动位置等用户上下文。

## 默认业务与后端

玩趣盒当前以本地单人业务、持久化及应用接续为主，没有云端服务端；旧 LAN 入口、适配器与网络权限已撤下，保留源码不代表功能可用。新任务未要求远程服务时，保持核心功能本地可用。需要云端时沿用目标后端技术栈与既有契约。

- 复用已有存储/传输服务，保持 I/O 边界集中；简单页面不为形式额外拆服务。仅在实际数据访问职责或复用需要时增加 Repository。
- UI 状态与序列化业务状态分开。边界校验后输出明确 DTO，`as` 不替代运行时校验；内部不重复解码。
- 按实际数据结构确定稳定 ID 与单位，格式或语义演进确有需要时定义版本。持久化合并频繁写入，在后台等关键边界保证待写入数据落盘；损坏输入与写入失败可定位且不伪报成功。
- 对实际可重叠的异步生成、请求或连接，按需使用取消或代次检查，防止旧结果覆盖新状态；不为所有同步操作添加并发框架。计时器、监听与原生句柄由实际 owner 在生命周期结束时释放。
- 生命周期按业务连接 UIAbility、NavDestination 和现有服务。明确隐藏、后台、暂停与恢复的语义；游戏只恢复自动暂停，不解除用户手动暂停，倒计时等场景不能直接套用游戏暂停规则。
- 接续与同步只传必要的可序列化值，在接收边界完成校验后一次提交恢复。修改存档格式或生成算法时，保留实际存在的旧数据恢复语义。
- 新增配套服务端时，只明确本次用例涉及的 DTO、错误码、权限和写入语义；分页、幂等、冲突策略按实际需求确定。错误码由客户端映射多语言文案。

## 推进与验收

先完成一条用户可用的端到端流程，再按已有组件和服务边界扩展。保持改动范围与任务一致；不创建无使用者的抽象、兼容层或云端基础设施。

按改动选择有意义的规则、存储、生命周期或协议测试；`.ets` 修改还需目标 SDK 原生构建。前端变更检查双主题、关键操作、适用窗口和字号；网络验证围绕本次协议的真实失败模式。低影响样式或文档修改不编写镜像测试。审查先追实际入口、调用方与数据范围，再验证问题；保留代码、静态猜测与已复现缺陷分别记录。

交付说明具体行为、变更位置、已运行检查及实际限制。区分静态检查、桌面模型测试、原生构建、模拟器、真机和真实后端验证；历史结果不能替代当前产物验收。应用升级优先覆盖安装并验证数据保留，不以卸载或清数据代替修复。
